## Coordinate and migration contract

`PostSummaryDto` and `PostDetailDto` now include required `coordinates: PostCoordinates | null`. The shared type/guard uses finite WGS84 decimal degrees: latitude -90..90 and longitude -180..180. Zero is valid; null means no confirmed location. This validates a global numerical range, not whether a point belongs to a particular administrative area.

Existing authenticated create/update endpoints accept a complete nested pair:

```json
{"coordinates":{"latitude":10.8231,"longitude":106.6296}}
```

For create, omitted/null coordinates store null/null. For update, omission retains the previous pair; `coordinates: null` clears both fields; a supplied pair replaces both. Partial pairs, nested nulls, numeric strings, extra fields, arrays and out-of-range values return 400 without writes. Existing R03 authorization remains in effect: Leader edits stay within the assigned active team; Admin can moderate other valid teams. Ownership/author/team-transfer fields remain rejected. Mutation responses retain their existing entity-shaped contract (including raw latitude/longitude); canonical reads expose the nested coordinates DTO.

Migration `1794931200000-AddPostCoordinates.ts` adds nullable REAL `Latitude`/`Longitude` columns and a named paired/range CHECK. It does not rebuild Post, alter historical migrations, modify existing identities/relations or guess a backfill. Existing posts stay unlocated. Rollback drops only these two new columns, intentionally losing coordinates while keeping posts/photos; it requires SQLite >=3.35. The tested native SQLite version is **3.44.2**. Apply compiled migrations before starting the new backend; no migration was run against the developer/production database in this workstream.

The focused migration tests use a populated pre-coordinate Post/Photo fixture with foreign keys, check null backfill and retained identities/content, reject invalid raw writes, check FK integrity, confirm replay is a no-op, and exercise rollback/reapply. Fresh full-history replay is separately covered by runtime smoke. This is not a claim that every historical production upgrade path has been rehearsed; that remains R11.

## Packaged geography and provenance

The supported minimal set is one generalized Vietnam outline from **Natural Earth 5.1.2, 1:110m**, plus the existing flower/frame SVGs. Natural Earth data is public domain ([official terms](https://www.naturalearthdata.com/about/terms-of-use/), [versioned upstream license](https://github.com/nvkelso/natural-earth-vector/blob/v5.1.2/LICENSE.md)). The boundary is context only: no provincial/commune coverage, current administrative precision, detailed offshore representation or navigation accuracy is claimed.

[Data README](../../packages/frontend/public/data/README.md) and [manifest](../../packages/frontend/public/data/index.json) record the pinned upstream URL, source SHA-256, extraction rule and hashes of all three required files. `scripts/package-map-assets.mjs` verifies the downloaded source and extracts only `ADM0_A3 === 'VNM'`, preserving its geometry and replacing properties with name/source. `--source <file>` supports an already downloaded source. Normal build/display uses the checked-in assets and needs no geography download.

`scripts/check-map-assets.mjs` checks file existence, exact supported paths, hashes, source/license metadata and closed finite polygon rings. It accepts an optional public/build directory argument. Scoped `.gitattributes` rules keep hashed assets at LF across platforms; existing SVG artwork content is unchanged. The GeoJSON has a specific `.gitignore` exception. Legacy `index2.json` remains untouched and unused; absent annotations/province files are not requested. Runtime also validates the manifest path, SHA-256 and geometry and aborts stale loads. Runtime hashing uses Web Crypto, requiring HTTPS or a trustworthy loopback origin.
