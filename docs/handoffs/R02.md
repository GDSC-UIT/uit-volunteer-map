# R02 — Campaign access and current account validity

Date: 17 November 2026 (Asia/Bangkok). Branch: `codex/r02-campaign-access-account-validity`, based on fetched `develop` `6b56a0170a8002986bc25279a398d16a2c6ecd3c`. Local commits only; no push, PR, merge, migration/schema change or developer DB mutation.

## Delivered behavior

- Campaign list/detail are anonymous reads. Invalid or stale credentials do not prevent an otherwise public read. Campaign POST/PUT/DELETE require a current Admin. Valid Leaders receive 403 and denied writes leave stored rows unchanged.
- JWT middleware accepts Bearer HS256 tokens with a positive integer Account ID and finite expiration. It verifies the signature/expiry and loads the current nondeleted Account plus Role. Deleted/missing accounts cannot use an old token; a role change takes effect immediately on protected requests instead of trusting the old JWT role. Account IDs remain distinct from User IDs.
- Login excludes soft-deleted accounts with the same generic invalid-credentials response. No credentials, password hashes or account details were added to error responses.
- `JWT_EXPIRES_IN` defaults to 1h. A positive integer means seconds; integer s/m/h/d suffixes are supported. Zero, negative, fractional, malformed and overflowing values fail configuration validation. Startup calls the same parser as token signing before opening the database/server. Only the example env file was changed; private environment files were preserved.
- `/api/verify` shares authoritative account checks. Valid response remains `{success:true,data:{isExpired:false}}`. Missing/invalid/expired/removed-identity tokens now return 401 instead of a misleading HTTP-200 signature-only result. Invalid-token middleware responses also standardize on 401 (previously 403); valid-user permission denial stays 403. These are intentional response-contract corrections.
- Focused R13 / **UX-013** companion: Admin and Leader logout invoke AuthProvider, immediately clear provider state, storage, in-flight queries and cache even if logout API fails. Axios preserves HTTP status/config and server message. Protected 401 clears only the matching current session; stale responses from an old token cannot clear a newer session. A valid 403 and failed login do not force logout. Browser-restored pages/storage changes synchronize client state.

Existing campaign CRUD payloads, database structure, role names, UI layouts and data adapters remain. No R03 ownership, R04 DTO/filter, R05 Guest integration, R06 map or admin/leader persistence work was included.

## Limits and integration dependencies

- PR #65 (accessibility) and #66 (responsive) remain separate, unmerged and unchanged. This branch starts from develop; it intentionally does not absorb their commits. Reconcile their small LeaderDropdown/AdminLayout changes during later integration and rerun combined checks then.
- Stateless logout does not revoke a copied valid JWT on the server. Account deletion/role changes are enforced per request; additional per-token revocation/session infrastructure is outside R02.
- Client state still restores from local storage and does not proactively call the server on every page load or run an expiry timer. A protected request returning 401 clears it; server authorization is always authoritative. A stale role can briefly affect presentation while backend requests enforce the current role.
- `/api/verify` HTTP/error semantics and invalid-token 401 are deliberate compatibility changes; no current frontend consumer was found beyond the shared route constant. External consumers must handle non-200 invalid sessions.
- R02 does not claim full R13 completion: broad lint/Node alignment, rate limiting, deployment CORS, validation-error cleanup and related hardening remain.
