## Result and review summary

Admin campaign/team pages previously displayed hardcoded records and inert controls. They now load actual campaign IDs, support basic create/edit/delete, show pending/error/success states, retain drafts after rejected writes, and preserve the selected campaign in `?campaignId=` across reload. Team search operates on the selected campaign's real list. Supported actions have visible buttons and inline delete confirmation; unsupported media/featured-activity buttons are removed from these pages.

Team creation previously set `Team.leader` without setting `User.team`, while deletion soft-deleted member profiles. Explicit assignment now changes both relations in one transaction. Empty-team deletion detaches membership and preserves all profiles/accounts. Linked posts or attachment metadata produce 409 instead of an accidental cascade or an opaque foreign-key error.

## Backend contracts and policies

| Endpoint | Access / result |
|---|---|
| `GET /api/admin/teams?campaignId=...` | Current Admin only. `AdminTeamReadDto[]`: existing public team fields plus actual nullable `leaderId` from `Team.leader`. Same strict filter parsing and campaign existence checks as R04. |
| `GET /api/admin/team-leaders` | Current Admin only. Active Leader profiles with active accounts: `userId`, `fullName`, nullable `assignedTeamId`, and `commandedTeamIds`. No passwords, emails, Account IDs or raw entity graphs. IDs are User IDs, not Account IDs. |
| Campaign POST/PUT | Existing Admin-only routes; now return canonical `CampaignReadDto`, including nullable description/attachment array. Trimmed nonempty names (max 200); real `YYYY-MM-DD` calendar dates; end date must not precede start, including a partial update combined with stored values. Unknown top-level fields are rejected. |
| Team POST/PUT | Canonical team DTO plus nullable `leaderId`. Create accepts omitted/null Leader, allowing team creation before account provisioning. Rename/description and optional existing image-URL API fields are supported. Campaign transfer remains unsupported/rejected. |
| Team assignment | Only Admin can supply `leaderId` on update, including null or the same ID. Leader retains own-active-team descriptive edits, with cross-team edits rejected. New names are trimmed, 3–100 characters. Existing globally unique name constraints are respected. |
| Lifecycle IDs | Campaign/team edit/delete use the existing canonical positive-safe-integer parser; malformed IDs are 400, missing resources 404. |

Assignment validates the selected profile, current active Account and role name `Leader`. A User assigned to another team, or referenced as commander by another team, returns 409; there is no silent transfer. The Admin must first explicitly clear the old assignment. Checks include legacy retained teams rather than silently reclaiming their commanders.

On explicit assignment/clear, old commander membership and additional Leader-role memberships in that team are detached; the chosen Leader is assigned to both relations. Ordinary members remain active and attached. This also repairs duplicate Leader memberships in the explicitly edited team; it is not a blanket migration/repair of every historical relationship. Deleted/inactive/wrong-role candidates are rejected, and unchanged unrelated teams are preserved. Tests prove that the old Leader loses own-team/post permissions and the replacement gains them via existing R03/R04 actor resolution.

| Delete operation | Policy |
|---|---|
| Campaign with any Team or campaign Attachment | **409**, including retained soft-deleted Team rows. No linked record is removed. |
| Team with any Post or team Attachment | **409**, including soft-deleted posts. Post/photo history remains readable under existing rules. |
| Empty active Team | Detach all `User.team` references, clear `Team.leader`, then **physically delete** the empty Team. No profile/account is deleted or deactivated. |
| Empty Campaign | Physically delete only the Campaign. |

The empty-team hard-delete policy replaces the previous harmful member-deactivation behavior. Foreign keys protect against linked writes racing with physical deletion. Attachment-bearing resources intentionally require a later explicit media-cleanup workflow rather than an implicit cascade. Legacy soft-deleted teams remain retained and can block campaign deletion; R07 does not purge them or provide restoration. Their globally reserved names can still conflict.

R07 lifecycle writes use a shared transaction queue for the datasource's single SQLite connection. It serializes these lifecycle requests so concurrent requests cannot share nested savepoints or claim one free Leader twice. All assignment/metadata changes roll back together on failure. SQLite constraint/busy failures become sanitized 409 responses; the queue continues after a rejected operation. This is a process-local SQLite coordination mechanism, not distributed locking for arbitrary other services. Helpers inside the transaction use its EntityManager rather than recursively queueing another lifecycle operation.

## Frontend integration

The existing Axios/auth client handles every read/write. Shared management types match the new contracts; separate Admin team/candidate query keys do not change public R04 DTOs. Successful mutations invalidate campaign/team/post prefixes plus Admin teams and Leader options, so active lists refresh and previously cached Guest details are invalidated. A 409 refreshes assignment options while preserving form state. HTTP status is retained by the existing client; role/session behavior from R02 is unchanged.

The forms edit only basic metadata and assignment. Existing team image URLs/attachments are preserved because the form does not submit replacements. No upload/provider behavior is newly claimed. Campaign and team selectors use returned IDs; candidate values are User IDs, with already occupied candidates disabled. Empty candidate lists permit an unassigned team, preparing the R08 bootstrap path. The Admin still needs R08 to create real Leader accounts/profiles.
