## Result and UX findings

The Leader screen now resolves its team from the authenticated `GET /leader/team`, then reads only that team's posts. There is no default team ID, URL-supplied team override, fake commander or placeholder activity. An unassigned Leader sees a truthful missing-assignment state.

- **UX-012 / P0:** team name/description edits and post create/edit/delete persist through the existing authorized API. Successful writes invalidate shared/public and management query prefixes. Failed writes retain the active form or confirmation; repeated pending writes are disabled. Saved changes survive refresh and sign-out/sign-in.
- **UX-014:** the actual gallery and activity list reflow at the tested widths. Named edit/delete actions stay visible without hover and do not cover the post link. Existing warm colors, background artwork, portrait frame and reusable post card/detail presentation remain.
- **UX-015 / UX-016:** native file input and named buttons replace inaccessible image-tile selection. Users can remove or move selected images before uploading, see the four-image limit, cancel, and recover after a partial provider failure. Already uploaded image URLs are reused when retrying or moving between steps; previews are revoked when removed/unmounted.
- **UX-017:** one parent editor keeps title/body, nullable coordinates, selected files and uploaded URLs across Back/Continue. The character count is real; empty trimmed text, incomplete coordinate pairs and out-of-range WGS84 coordinates cannot be submitted. Zero is a valid coordinate.
- **UX-023, scoped:** the R09 team editor, image chooser, post editor and delete confirmation use a named native modal, an explicit Tab/Shift+Tab loop, Escape handling, inert background and focus restoration. Pending writes/uploads block dismissal. Delete identifies the affected post and initially focuses the safe Close control.
- **UX-024, scoped:** R09 amber action buttons use black text. This does not claim a whole-app contrast audit.

Commander assignment is Admin-only under R07/R08; the old nonfunctional commander editor trigger is no longer shown. The team gallery reads existing images/attachments; unsupported image editing and fake location/geocoder dropdowns are not presented. No HTML prototype or broad redesign was created. The separate shared accessibility/responsive branches were not merged wholesale.

## Existing contracts used

All requests use the existing Axios client, Authorization/session behavior and API envelopes. The generic management write helper was extracted for reuse, not replaced by a second client.

| Operation | Contract used |
|---|---|
| Own team | `GET /api/leader/team` → safe `TeamReadDto`; missing assignment is 404. |
| Team metadata | `PUT /api/teams/:teamId` with only `teamName` and nullable `description`; no campaign or commander assignment fields. |
| Team posts | `GET /api/posts?teamId=…&campaignId=…` → summaries; detail reads the canonical public DTO. |
| Create post | `POST /api/posts` with title/content, own team ID, nullable coordinates and uploaded photo URLs; existing backend returns **200** and derives author from the authenticated account. |
| Edit post | `PUT /api/posts/:postId` with title/content/coordinates only. Existing photos are displayed and preserved; no ownership transfer or unsupported photo replacement. |
| Delete post | `DELETE /api/posts/:postId`, existing soft-delete behavior; related public queries are invalidated. |

Reloadable protected routes: `/leader/posts/new`, `/leader/posts/:postId`, `/leader/posts/:postId/edit`. Detail/editor reject a post belonging to another team. Server authorization remains authoritative; an actual cross-team PUT returned 403 during browser validation.

The write response is treated as an entity ID, not falsely typed as `PostDetailDto`: after saving, the destination route loads the canonical detail. The editor snapshots the original team, so a refreshed assignment to another team blocks saving and retains the text instead of silently transferring the draft. Mutations do not retry automatically.

A create failure with no HTTP response or HTTP 5xx is explicitly **unconfirmed**, because the current backend may already have saved part of the operation. The draft remains and the submit action is blocked. The user can open the real list in a separate tab, then explicitly acknowledge checking it before manually allowing another attempt. This reduces accidental duplicates; it is not an idempotency or transaction guarantee.

## Remaining dependencies and next scope

1. **R10 — next implementation:** branch `feat/r10-media-atomic-persistence` from this R09 branch while the stack remains local. Make post+photos and supported team+attachments writes transactional; add deterministic persisted photo order/thumbnail with a new forward migration/backfill. Constrain the existing Cloudinary helper's file size/type/count and handle provider configuration/failure through this same flow. Prove rollback with an injected DB failure, duplicate URL/conflict, retry and ordering tests. Keep one provider/client and avoid a local-disk upload API.
2. Existing post creation saves Post before Photo rows; a failed photo insert may leave a partial Post. An interrupted response can still make a manual retry ambiguous. The UI safeguard does not resolve this release dependency. External provider assets can also remain orphaned after removing/canceling uploaded images or a DB failure; R10 must document the cleanup boundary.
3. Editing existing photo sets/order and changing team attachments are not offered in R09. Existing team images and post photos remain viewable; R10 should extend only against agreed backend contracts.
4. Drafts live in component memory and survive the active form's recoverable save/upload errors and Back/Continue. They are not persisted across a confirmed page exit, forced reload, logout or a 401 session invalidation. Browser reload/close gets the existing unsaved-work warning where supported. This is not offline recovery or cross-session draft storage.
5. **R11**, after R10's schema settles: fresh/historical migration and seed replay plus restore policy. Then **R12/R13** dependency/setup/error/security hardening; **R14/R15** combined real journeys, CI and focused release acceptance. Shared accessibility/responsive PR integration remains a separate stack dependency; no PR was merged here.
6. Live Cloudinary behavior and production deployment are unverified. R09 has no remote CI run because it was not pushed. Recheck the combined integrated branch before release; inherited R08 token-reset and runtime limitations remain in [R08](R08.md).
