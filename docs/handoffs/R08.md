## API contracts

All `/api/accounts` endpoints require a current Admin through the existing R02 middleware. They manage **Leader accounts only**; Admin accounts are excluded from this namespace and return 404 on detail/update/deactivation. Role IDs, roles, account/User identity overrides, activation flags and team assignment fields are not accepted in provisioning/update bodies.

| Endpoint | Contract |
|---|---|
| `GET /api/accounts` | `ApiResponse<LeaderAccountReadDto[]>`, including active and inactive Leader accounts and truthful missing/archived profile states. |
| `GET /api/accounts/:accId` | Safe detail DTO, including inactive records for Admin review. Canonical positive-safe-integer IDs; malformed 400, missing/non-Leader 404. |
| `POST /api/accounts` | 201 with the safe new account/profile DTO. Account + User are committed together, unassigned. Role is selected using `roleName === RoleEnum.LEADER`, never numeric ID 2. Missing configured role returns 409 with no writes. |
| `PUT /api/accounts/:accId` | Partial profile fields and optional password reset. Login username/role/assignment are immutable here. Omitted password preserves its hash; empty changes are 400. Inactive accounts and archived profiles are 409, not silently restored. |
| `DELETE /api/accounts/:accId` | Idempotent **deactivation**, not physical deletion. Clears the User's team membership and every matching `Team.leader` reference, then disables Account, in the shared R07 transaction queue. Returns the safe inactive DTO. |

`LeaderAccountReadDto` contains `accId`, username, literal Leader role, account-active status, nullable stored timestamps, nullable public-to-Admin profile fields, nullable team/campaign summary and `commandedTeamIds`. Profile includes its own **User ID**, fullName, MSSV/class/email/phone and profile-active status. It never includes password/hash, Role ID, JWT or a raw Account/User entity graph. These profile fields are Admin-only data; public team/post DTOs remain unchanged.

This intentionally standardizes previously inconsistent bare-array/raw-entity account responses into the existing API envelope. All internal account-page consumers now use that contract. Read profile names are `profile.fullName`; the existing provisioning write spelling **`fullname`** is retained:

```json
{
  "username": "synthetic-leader",
  "password": "synthetic-initial-password",
  "fullname": "Synthetic Leader",
  "mssv": "99000001",
  "class": "SE.01",
  "email": "fixture-leader@gm.uit.edu.vn",
  "phoneNumber": "0900000000"
}
```

The example is synthetic and sends no message. Creation requires these identity/profile fields. Existing provisioning rules are retained: MSSV has eight characters, class is at most 15, phone has at least ten characters, and new/changed provisioning email belongs to `@gm.uit.edu.vn`. Names/username are trimmed and bounded. Email writes are normalized to lowercase; uniqueness checks include retained profiles and case variants. Usernames remain globally reserved even after deactivation. Passwords keep the existing six-character minimum and additionally reject values over **72 UTF-8 bytes**, preventing silent bcrypt truncation. Password bytes are not trimmed; hashes use bcrypt cost 10.

For existing profiles, nullable MSSV/class/phone may be cleared explicitly. The form sends only changed fields and omits a blank password, so unrelated edits preserve legacy profile values, including unchanged older email addresses. A missing profile requires complete profile fields to repair against the same Account; a password-only update cannot create an incomplete replacement. Archived profiles are not automatically unarchived. There is no teamId on account provisioning: create the account/profile, then assign its User ID through R07.

## Identity, assignment and session behavior

Creation, profile repair/update and deactivation use R07's transaction-aware EntityManager and shared SQLite lifecycle queue. Account creation is rolled back if User insertion fails. Profile/password changes roll back together. Assignment release is rolled back if disabling the Account fails; the queue remains usable after failure. Concurrent R07 assignment and R08 deactivation cannot leave that disabled user commanding the team in the tested single-process datasource.

Deactivation clears both relation directions, including legacy matching commander references, while retaining User IDs, profile deletion state, authored Post/Photo records and other accounts. Historical author summaries can still identify the retained User. The Account is not reactivated by an edit, and inactive records stay visible in the Admin list. The process-local queue is not a distributed-locking claim for every possible external writer.

No new token format or auth middleware is needed: R02 rechecks the current Account on protected requests. A session token that worked before deactivation receives **401** afterward, and a new login is denied. The existing frontend client/provider clears that rejected session when the protected request fails. This is request-time enforcement, not a push logout of an otherwise idle page.

Password reset changes future password authentication. It **does not separately revoke already issued JWTs** while the account remains active; deactivation or normal expiry still invalidates them under the current token model. No token-version migration or reactivation policy is claimed here.

Successful management writes invalidate account, Leader-option, Admin-team and public campaign/team/post query prefixes. R07 assignment mutations also invalidate the account list, so its campaign/team display stays current. Failed writes keep the form/confirmation; a 409 refreshes related management reads without replacing the editing snapshot or clearing typed credentials.
