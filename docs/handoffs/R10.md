# R10 — Atomic media persistence and bounded upload

Date: 18 November 2026. Branch: `feat/r10-media-atomic-persistence`, based on R09 `049fc48`. Local only; no push, PR or merge.

## Implementation

- Post create + all Photo rows commit together using the existing SQLite lifecycle transaction queue. Post update/delete/photo append also use that queue, with team/actor authorization checked inside the transaction.
- Team create already grouped metadata/assignment/attachments in R07. Attachment append now uses the same transaction queue, rechecks its active parent/access and saves the entire batch atomically.
- A duplicate image URL or injected later-image DB failure returns 409 and rolls back earlier inserts, metadata, assignment and thumbnail/position changes. Concurrent appends cannot bypass the four-live-photo/four-team-attachment quota within this datasource.
- New forward migration `1795017600000-AddPhotoPosition` adds non-null `Photo.Position`. It preserves the previous first-flag/PhotoId presentation order, partitions by PostID, keeps archived/orphan rows and normalizes one first flag among live photos. Existing migrations are unchanged. Restart is a no-op; down removes Position but does not reconstruct contradictory historical flags.
- Public photo DTOs now include `position`; order is Position then PhotoId, and exactly the first visible photo has `isFirstImage=true`. Summary thumbnail matches detail's first photo. Create uses input array order; legacy isFirstImage hints do not override that order. On single-photo append, an explicit isFirstImage=1 promotes the new photo and shifts existing live positions transactionally; otherwise it appends.
- The existing Cloudinary helper/picker share limits: four images, JPEG/PNG/WebP/GIF, nonempty, at most 5 MiB each. A batch is preflighted before any network request. Configuration, HTTP failure, malformed response/URL, network error, timeout and abort reject cleanly. Existing partial-success URLs remain reusable in the R09 editor. Metadata image URLs must use HTTP(S); no local-disk API or second provider/client was added.
- Legacy collections above the new limit remain readable; further appends are rejected rather than deleting historical media.

## Boundaries

Client file/MIME checks improve UX, not security against a crafted direct request. The actual unsigned Cloudinary preset must independently restrict image formats/size and permitted upload behavior; live preset/CORS/quota policy remains unverified. No credentials, signing service or provider deletion API was introduced.

SQLite rollback cannot remove already uploaded external assets. Canceling/removing a successfully uploaded file, an upload response lost in transit, or a later DB failure may leave a provider orphan. R09 retains successful URLs for retry while the editor remains mounted; operator/provider cleanup remains a documented deployment dependency. The 60-second timeout bounds the client request, not remote asset creation.

Atomic DB writes do not make an interrupted successful POST idempotent. The existing R09 unconfirmed-result/manual-check safeguard remains. No offline/cross-session draft persistence, existing-photo replacement/reordering UI or new attachment editor is claimed.
