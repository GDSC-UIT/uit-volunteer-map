## Implementation and evidence

**Seed:** default seed only ensures role names, preserving existing numeric IDs. `--demo` requires an explicit DB path, non-production environment and two caller-supplied 12+ character passwords within bcrypt's 72 UTF-8 bytes. A fresh synthetic dataset has separate Admin/Leader accounts/profiles, a real assignment, a labeled campaign/team, two posts/illustrative coordinates and packaged existing artwork. Account/profile/assignment/media seed writes share a transaction. Reruns preserve passwords/content; conflicts, incomplete namespaces and non-demo data are refused.

**Schema:** the R06 inline coordinate CHECK already worked in SQLite, but TypeORM did not read it and proposed rebuilding Post on every schema comparison. New migration `1795104000000-NormalizeCoordinateCheck` preserves its behavior using a table-level CHECK, including live Post/Photo links. Final schema comparison has **zero proposed queries**. Historical migrations were not edited. The representation-only down keeps the check/data; down/reapply on populated data was also exercised without changes.

**Maintenance:** `npm run db:tool -w @uit-volunteer-map/backend -- …` offers read-only inspect, verified backup, guarded upgrade, restore to a new path and explicit legacy recovery. Source paths are mandatory, existing targets refused, and backup uses SQLite's backup API so committed WAL content is included. Upgrade supports only exact known migration prefixes from 12 onward; unknown histories/FK violations are refused. Recovery supports the tested first-three ledger/column generation and requires an explicit mapping/timestamp; the source is read-only and never replaced.

**Historical correctness:** normal migration 4 still fails on populated first-three-migration data with `NOT NULL constraint failed: temporary_Post.CreatedAt`; the normal runner rolls back and retains the original rows/three-entry ledger. A later forward migration cannot execute before that failure. The supported remedy is export/transform/import into a freshly migrated target, preserving original source and archive.

Historical Post.CampaignId is not silently copied to TeamId. The rehearsal uses Campaign **7**, Team **70**, Post **700** and requires the reviewed mapping `700 → 70`; mapping to 7 is rejected. Existing IDs, author, membership, password hashes, content and URLs are retained. Missing timestamps use the explicit plan value and coordinates remain null. Removed legacy columns, including Status/Campaign.UserId and original CampaignId, remain in the private archive. This preserves lineage without inventing event dates or ownership.

**Confirmed login issue:** a Leader logout can retain a protected Leader return URL. Logging in next as Admin previously returned to that forbidden route. Login now accepts a private return URL only for the corresponding role, preserving same-role deep links and safe public URLs. No backend authorization was relaxed. The complete same-tab Leader→Admin browser journey passed after this small fix.

## Supported-baseline and remaining release gates

- Read-only local metadata showed the existing developer DB has **12 migrations**, lacks the new coordinate/order columns and remained unchanged. The populated 12→15 validation used a synthetic historical-schema fixture, not a migration of that developer file.
- **No deployed DB was accessed.** A production operator must inventory the actual ledger/schema and rehearse the corresponding path against a verified backup before cutover. Other histories/manual structural variants are not declared supported. The tool checks the legacy column generation, not a cryptographic attestation of arbitrary external DB contents.
- Backup/restore targets and raw recovery archives contain sensitive records/hashes. Use an access-controlled directory and retain them outside Git; Windows directory ACLs still matter. No real backup, private rows, passwords or credential-bearing logs were committed here.
- Historical bootstrap migrations still create legacy sample accounts; their production deactivation/reprovisioning decision remains a deployment gate. The new demo accounts have no built-in password and the demo seed is disabled in production.
- The CHECK normalization's down deliberately retains the invariant; a Git revert or blind migration revert is not full DB rollback. Stop writers for upgrade/recovery, inspect failed candidates and restore into a new file with the matching app version before a controlled DB_PATH cutover.
- R10's live Cloudinary preset/CORS/quota validation and external-orphan cleanup boundary remain. R11 adds no new provider, backend persistence endpoint, dependency or HTML prototype.
- Remote CI was not run: neither R10 nor R11 was pushed. Existing shared accessibility/responsive PRs and the functional stack remain unmerged.
